# Long-Running One Piece Character Parser Improvement

You are one of exactly two agents working concurrently in the same Git
worktree. Work as a coordinated pipeline until every remaining One Piece
Character card has a consistent, exact transformation from printed card text
to the generated ability representation.

This is an implementation task, not a report. Continue set by set and card by
card. Do not stop merely because a mismatch is difficult, CI is queued, or one
set is complete.

## Invocation Contract

Launch exactly two long-running runs with this same prompt and assign one
explicit role to each:

```text
ROLE=AGENT_A
SESSION_ID=<same stable identifier for both runs>
```

```text
ROLE=AGENT_B
SESSION_ID=<same stable identifier for both runs>
```

Do not infer or switch roles. If `ROLE` or `SESSION_ID` is missing, duplicated,
or conflicts with the other run, stop before editing and request a corrected
assignment. There must be exactly one Agent A and one Agent B.
Neither agent may spawn additional agents or delegate work to another run.

At startup, each agent reports:

- role and session id
- absolute worktree path
- current branch and HEAD
- dirty paths within its ownership
- current set and inventory counts, recomputed from disk
- first file it intends to claim

The prompt is intentionally state-independent. Reconstruct progress from the
worktree, inventory, Git history, and existing PR rather than assuming a named
set or historical commit is still current.

## Goal

For every Character card in every inventoried set:

1. Compare the exact printed English card text with the current generated
   ability representation.
2. Decide whether the representation is exact and semantically complete.
3. When it is not, improve the generalized parser or shared effect model so
   similar wording is handled correctly.
4. Regenerate or update the affected card definitions.
5. Prove the transformation with focused parser tests.
6. For every changed card or newly supported engine behavior, prove the happy
   path through `OnePieceTestEngine`.
7. Finish each set with zero unexplained Character mismatches, then commit,
   rebase onto `origin/main`, and push that set as one checkpoint.

The desired result is a self-improving parser. Prefer one generalized parser
fix that corrects a family of cards over hand-authoring one card. A card-specific
override is acceptable only when the wording is genuinely unique and the reason
is documented.

## Two-Agent Contract

The agents have distinct ownership. Do not both edit the same file.

### Agent A: Parser and Set Integrator

Agent A owns:

- parser production code
- parser unit and integration tests
- effect/type extensions
- engine production changes required by new effect shapes
- generated Character definitions and canonical/reprint corrections
- inventory regeneration
- set-level validation
- all staging, commits, rebases, conflict resolution, pushes, and PR updates

Agent A is the only agent allowed to run Git operations that mutate repository
state. Agent A must never use blanket staging in this dirty shared worktree.
Stage only the reviewed files belonging to the completed set.

### Agent B: Independent Semantics and Behavior Verifier

Agent B owns:

- independent printed-text versus ability review
- identifying dropped costs, conditions, targets, alternatives, durations,
  zones, quantities, restrictions, replacement semantics, and trait splits
- finding comparable existing cards and parser tests
- command-driven tests under `packages/engine/tests/cards`
- focused verification of engine behavior
- concise handoff packets to Agent A

Agent B must not edit parser production files, generated card definitions,
effect/type production files, inventory output, or run mutating Git commands.
When a production change is needed, report the exact expected representation
and evidence to Agent A.

### Shared-Worktree Safety

- A file must have one active owner. Announce `CLAIM: <absolute path>` before
  editing and `RELEASE: <absolute path>` after the focused check or handoff.
  Claim the smallest useful set of files and never claim a directory wholesale.
- A claimed file remains owned until released, even if the owner is waiting on
  a test. If a claim appears stale, contact the owner; never assume abandonment
  and overwrite it.
- Publish a heartbeat whenever a focused command finishes and at least every
  10 minutes during longer work. If the other role misses two heartbeat
  intervals, pause all writes and ask the user to restart or explicitly retire
  that role. Never seize its claims automatically.
- Communicate before touching any file outside your ownership.
- Before generation, formatting, broad validation, commit, or rebase, Agent A
  sends a pause request. Agent B finishes its current file write, reports the
  paths changed and running commands, and acknowledges the pause.
- Agent A waits for that acknowledgement before proceeding.
- Agent B resumes only after Agent A reports the new HEAD and confirms the
  worktree is ready.
- Never run two formatters, generators, installs, rebases, commits, or broad
  test commands concurrently.
- Read-only searches and independent focused tests may run concurrently.
- If either agent sees an unexpected modification, stop editing that file and
  ask the other agent who owns it. Never overwrite, restore, stash, or discard
  another agent's work.
- Only Agent A resolves merge or rebase conflicts. Agent B supplies semantic
  review when requested.
- Never use `git stash`, `git reset`, `git checkout --`, blanket cleanup, or
  blanket staging. Existing modifications belong to one of the agents or the
  user until proven otherwise.

### Coordination Channel

Prefer direct agent-to-agent messages when the execution environment supports
them. If it does not, use a worktree-local, untracked mailbox rooted at:

```bash
git rev-parse --git-path "codex-one-piece-sync/$SESSION_ID"
```

Create one status file per role:

```text
agent-a.md
agent-b.md
```

Each agent writes only its own status file and reads the other agent's file.
Never stage these mailbox files. Every status update includes a monotonically
increasing sequence number, timestamp, current action, claimed files, last
completed evidence, requested pause state, and next handoff. Do not have both
agents append to one file.

Before either agent begins production work, complete this handshake:

1. Agent A publishes `READY A` with branch, HEAD, set, and claimed files.
2. Agent B publishes `READY B` with the same branch, HEAD, set, and claimed
   files.
3. Both verify that the branch, HEAD, worktree, and set agree.
4. Agent A publishes `START <set>`.
5. Agent B acknowledges it before either agent edits.

If direct messaging and the mailbox are both unavailable, do not run
concurrently. Report the coordination blocker instead.

## Concurrent Pipeline

Keep both agents useful without colliding:

1. Resume a partially modified set before selecting a new one. Otherwise choose
   the newest incomplete set in inventory order and then continue backward
   deterministically. Agent A publishes the selected set; Agent B must
   acknowledge it before scouting.
2. Agent B scouts one to three cards ahead. For each card, it sends Agent A a
   handoff packet containing:
   - card id, name, set, and definition path
   - exact printed text
   - current audit result
   - current representation
   - expected representation
   - discrepancy category
   - likely generalized parser rule
   - comparable cards or tests
   - proposed command-driven happy-path test
   - any rules uncertainty
3. Agent A implements the oldest ready packet as one coherent parser patch,
   adds the smallest rejecting parser fixture, and audits the card.
4. While Agent A implements card N, Agent B may:
   - write or run the behavior test for completed card N-1, and
   - scout card N+1.
5. Agent A does not declare card N complete until:
   - focused parser tests pass,
   - the single-card audit passes,
   - the generated representation was manually compared with every clause of
     the printed text, and
   - any required command-driven behavior test passes.
6. After a generalized fix, Agent A reruns the set inventory immediately.
   Newly passing cards still receive a quick manual semantic review; an audit
   pass is necessary but not sufficient if the comparator can miss meaning.
7. Agent B does not start a behavior-test file until Agent A has published the
   expected final ability shape for that card. Agent A does not edit a claimed
   behavior-test file unless Agent B releases it.
8. Keep the pipeline bounded: Agent B may scout at most three unresolved cards
   ahead. If the queue is full, it reviews already implemented cards or helps
   reduce a focused failing test instead of creating more speculative work.

Use short coordination messages:

## Card Loop

Process cards deterministically in inventory order. For each Character:

1. Run its audit from `tools/op-card-parser`:

   ```bash
   vp run audit:character -- CARD_ID
   ```

2. Read the printed text and current ability definition clause by clause.
3. Check all of the following explicitly:
   - trigger and timing
   - activation and optionality
   - every cost, including resting DON or the source card
   - source and destination zones
   - target owner, card category, color, attribute, trait, name, cost, and power
   - `up to`, exact count, and `any number`
   - `this card`, `other`, and `other than this Character`
   - conjunctions and alternatives
   - durations and expiry boundaries
   - opponent-effect versus all-effect restrictions
   - replacement effects
   - permanent versus triggered effects
   - canonical card and reprints
   - exact trait splitting
4. Add a focused failing parser test before or with the generalized parser fix.
5. Implement the smallest general production change.
6. Regenerate or update affected definitions through the repository's existing
   parser workflow. Do not mechanically overwrite unrelated hand-authored work.
7. Run the focused parser test and the single-card audit.
8. Add or update a `OnePieceTestEngine` happy-path test for each changed card.
   Exercise public engine commands such as `playCard`, `activateEffect`,
   `declareAttack`, `attachDon`, prompt selection, `endTurn`, or another real
   interaction. Do not use `validateCardAbility` or metadata-only assertions as
   proof.
9. If the card exposes a shared engine gap, add the focused shared-module test
   as well as the card behavior test.
10. Rerun the set inventory and record the next mismatch.
11. Search the full catalog for the newly supported wording. Audit any
    collateral cards changed by the generalized rule, including earlier sets;
    do not silently accept regenerated differences outside the current card.

Vanilla Characters require printed-text and export review but no fabricated
ability or behavior test.

## Parser Design Rules

- Preserve exact meaning; do not accept a lossy representation merely because
  generation succeeds.
- Model target intersections explicitly. For example, "green Event" means
  color green AND category Event, while "Slash attribute card or green Event"
  is an OR of two complete alternatives.
- Preserve costs independently from effects.
- Preserve qualifiers on replacement-effect protected targets.
- Preserve card-category reveals from hand, not only trait-based reveals.
- Permanent protections must encode who or what may cause the affected action.
- Canonical definitions and reprints must agree with the text of that printing.
- When adding a new effect or filter union member, update every exhaustive
  consumer: targeting, permanent evaluation, projection, validation, and tests.
- After fixing a reusable phrase, search the full catalog for the same wording
  and audit affected cards.
- Parser success is not semantic proof. The audit comparator can miss a wrong
  player, source, duration, conjunction, replacement qualifier, or scaling
  rule, so manually compare every printed clause with the generated object.
- Do not flatten repeated or proportional effects into a fixed value. Preserve
  “for every”, zone-count, rested-DON, and similar scaling inputs explicitly.
- When printed text contains multiple replacement consequences, preserve their
  order and required costs instead of retaining only the first action.

## Set Completion Gate

A set is complete only when:

- every Character in the set is exported
- every text-bearing Character reports audit `pass`
- every vanilla Character reports `vanilla`
- mismatches are zero
- all changed cards were manually checked against printed text
- focused parser tests pass
- focused engine/card behavior tests pass
- parser package tests pass
- engine package tests pass
- type checks for changed packages pass
- the inventory has been regenerated
- `git diff --check` passes
- Agent A reviewed the complete set diff for accidental regeneration or
  unrelated files

At the set checkpoint:

1. Pause Agent B and receive its changed-file handoff.
2. Verify that Agent B has released every file and no command is still writing
   to the worktree.
3. Run the set-level gates locally.
4. Inspect unresolved PR review threads and current CI status once if a PR
   exists. CI is asynchronous evidence, not a per-card gate. Do not wait ten
   minutes for queued checks before making parser progress.
5. If CI already reports an actionable failure related to this branch, fix it
   before publishing the checkpoint. Record unrelated, pending, or queued checks
   and continue.
6. Review `git status`, `git diff --stat`, `git diff`, and `git diff --check`.
   Separate user-owned or next-set changes from the checkpoint; do not include
   them merely because they are already dirty.
7. Stage only intended set/parser/test files by explicit path.
8. Commit exactly once for the completed set with a message such as:

   ```text
   improve One Piece OP12 character parsing
   ```

9. Fetch and rebase the committed checkpoint onto `origin/main`.
10. Resolve conflicts semantically, rerun at least the focused smoke gates, and
   review the rebased diff.
11. Push the branch and update the existing PR. Create a PR only if none exists.
12. Check CI once after the push, record the state, and resume Agent B with the
    new HEAD and next set. Do not poll pending checks unless they have already
    failed with actionable output.

Do not amend an already published previous-set checkpoint merely to include the
next set. Do not wait for GitHub CI before starting the next set unless CI has
already produced a specific actionable failure.

## Recommended Validation

Use the smallest rejecting check after each patch. At the end of a set, broaden
validation.

From `submodules/one-piece/tools/op-card-parser`:

```bash
vp run audit:character -- CARD_ID
vp run inventory:characters -- --set SET_ID
vp test run path/to/focused-parser.test.ts
vp test
vp check
```

From `submodules/one-piece/packages/engine`:

```bash
vp test run tests/cards/SET_ID/CARD_FILE.test.ts
vp test
vp check
```

From the repository root, after package-local gates:

```bash
pnpm run ci:one-piece:check
```

The root gate is required at set checkpoints when practical, but it must not be
run after every card. If it is skipped because of a known unrelated baseline
failure or time cost, state the exact reason and rely on the passed package-local
gates before committing.

## Stop Conditions

Continue until all Character sets are complete. Stop early only when:

- a rules or architecture decision cannot be derived from official text,
  comprehensive rules, comparable cards, or existing types;
- the same focused failure remains after a minimal reproduction and one
  reasonable fix attempt;
- the shared worktree cannot be made safe without discarding another agent's
  changes;
- credentials or remote access are required and no local substitute exists.

Queued GitHub CI, a long test runtime, the end of one set, or a parser mismatch
is not by itself a blocker.

When blocked, leave the current set uncommitted unless it independently passes
the completion gate. Report the exact card, printed clause, current and expected
representations, files changed, commands run, error output, and next smallest
action.
