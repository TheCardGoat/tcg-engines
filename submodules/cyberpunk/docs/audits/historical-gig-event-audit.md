# Historical Gig event facts (read-only audit)

Scope: all ten authored cards with `gigStolen`, `gigRolled`, `gigValueChanged`, or `gigsSwapped` triggers in `packages/cards/src/cards` (searched 2026-09-24). This report records the current contract and a proposed data boundary; it makes no runtime change.

## Rule boundary

Rule 10.16.1 makes a **trigger condition** a fact of the action that occurred; simultaneous triggers all become pending (10.16.2), and a separate pending effect can change state before another resolves (10.12, 10.14). A condition that must be true **during resolution** is checked then (10.15.1). If a piece is no longer valid, resolution uses last known information (10.10.1). The location of `if` matters: Kerry's “When you roll a min or max value” is part of the trigger; Rogue Preem Solo's “When a friendly Legend steals a Gig, if its value is even…” can be a condition on the pending effect. The rules mirror does not settle whether that `if` tests steal-time or resolution-time value. Freeze only verified trigger predicates; decide conditional instructions and effect selectors separately.

### Reachability of deferred matching

The direct-attack path calls `processEventTriggers` immediately after moving stolen dice (`moves/resolve-attack.ts:985-1006`). Gain-Gig does likewise for the roll event (`moves/gain-gig.ts:94-108`). Card-effect steals emit events inside `handleStealGig` (`effects/handlers/index.ts:1535-1585`) and enqueue them immediately after that effect resolves (`ability-executor.ts:1248-1269`), or at the end of a selected effect-target move (`moves/resolve-effect-target.ts:275-296`). These paths create an interval between event production and matcher evaluation, but this audit found no authored card sequence that changes the relevant die, thief, or attachment in that interval. The live reads are structurally vulnerable to such an intervening change; source departure and host reassignment **before matching** are hypothetical, not reproduced current-card failures. State can change **after matching and before pending resolution** through ordered triggers (10.12, 10.14), but the treatment of each later `if` still needs a ruling.

## Exact event-time facts needed for a coherent contract

1. `gigStolen`: preserve the existing actor, prior/new owner, source card ID, and ordered die IDs; add **per-die trigger snapshots** `{dieId, dieType, faceValue}` at the steal. A bundle-wide value cannot represent two different stolen dice. For source predicates capture thief effective power, controller, effective card types/classifications, and field/zone status at steal. Host matching needs the ability Gear's host ID at steal or an equivalent event fact. These fields support trigger admission; this audit does not require all pending effects to use their frozen values.
2. `gigDieRolled`: use the existing `dieType` and `result` for event-filter sides/range/parity and Kerry's **trigger admission** min/max condition. If the later d20/amount instruction must refer to the accepted roll, carry result/type into that evaluation too; decide that instruction's timing from a rules ruling first. Preserve replacement ordering: provisional gain-Gig result is not a second kept roll (10.25-10.26).
3. `gigValueChanged` and `gigsSwapped`: current Meredith filters have the necessary historical actor, direction/values, and prior owners. Keep them; do not replace `fromPlayerIds` with post-swap live ownership.
4. Separate **event facts used for trigger admission** from **resolution conditions and targets** in types and evaluation. A bare `contextTargets` ID remains useful for adjusting the stolen die (V Roamer) or selecting a new rival Gig (Gorilla Arms), but it cannot prove a past threshold, type, power, or source status. Establish reachability and the correct `if` timing before adding parity-drift assertions; test admitted triggers against their captured facts.

No event/type/card implementation was changed in this audit. The timing of Rogue Preem Solo's parity, Kerry's later d20/amount branch, Wraith's value, and Maelstrom's `if it's equipped` needs a ruling before their resolution behavior changes. The trigger-admission contract findings do not depend on those rulings.
